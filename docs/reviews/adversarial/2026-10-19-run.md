### F1 — P2 — A rescan purges the curated `replacedAtPath` row that placeRecord kept as history
- File: VideoScan/VideoScan/Volumes/VideoScanModel+ScanMerge.swift:537
- Invariant: VOL-4
- Key: VideoScan/VideoScan/Volumes/VideoScanModel+ScanMerge.swift#commitScanResults#VOL-4
- Claim: B2.4/d1f360660 (in range) made `placeRecord`'s `retire` keep a curated row at a path when a job lands different bytes there. That row is `removedFromCatalog/replacedAtPath`, "kept in the catalog's history … nothing purged", and sits beside its successor at the **same** `fullPath`. `CatalogCutoverB24Tests/balanceAudioRerunKeepsCuration` pins this with a Balance Audio rerun. The scan merge removes every row at a re-seen path, though:
  - `leaving` (complete merge :537–542, partial merge :670–674) is "under root && `newPaths.contains(fullPath)`", so it matches both rows.
  - `records.removeAll(where: leaving)` drops both, and `purgeCatalogRows(ids: replacedIDs)` purges both ids from catalog.sqlite.
  - The fresh record carries only the successor's values. The new live-wins pass ranks the successor above history (`sharedPathRank`), so that part is by design.

  Concrete sequence:
  1. The person stars a clip, writes a note and sets a date.
  2. The file is replaced (Balance Audio rerun reusing the name, or a Repair) and becomes `[history(curated), successor]`.
  3. Rescan or Update Catalog on that folder.
  4. The history row is gone from `records` and purged in the store. Stars 4, the note and the date are no longer in the catalog, and a `derivedFrom` or footage pointer at that id now dangles.

  A second shape: two **live** rows at one path (`keepBoth` / `retire`'s "NOT RECORDED … both stay in the catalog"). The earlier row is purged the same way. Since this range, the live-wins pass also keeps the **last** active row while the snapshot keeps the last *worth-restoring* one. So when the later row is uncurated (and `restoredFromSnapshot` contains the path), it now overwrites the curated values the snapshot had already carried onto the fresh record.

  Coverage: `AdvRescanEditDuringScanTests` asserts only on `fresh`. No test pins that the history row survives a rescan.
