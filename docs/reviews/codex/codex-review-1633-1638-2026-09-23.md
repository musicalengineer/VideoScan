## Delete/archive merges (#1633): changes required

### D1 — P1: unsupported-filesystem Combine publication can overwrite another writer

`VideoScan/VideoScan/CombineOutputPublish.swift:154–160` checks a reserved
placeholder with `lstat`, then calls ordinary `rename`. If another writer
replaces the placeholder after that check, the rename overwrites its file.
The ENOTSUP/EINVAL fallback does not provide the promised exclusive publication.

**Reproduced:** a deterministic syscall wrapper inserts `OTHER WRITER` between
the check and rename; publication succeeds and the destination contains
`NEW COMBINE`. Use a genuinely exclusive primitive, or refuse publication and
preserve the output when the filesystem cannot provide it.

### D2 — P1: a completed output reported as kept can be swept later

`PartialFileNaming.swift:194–206` unregisters the partial even when its rename
to `.vs-kept.` fails or the kept name exists. It retains the `.vs-partial.` name,
so `sweepStale` at 222–250 can permanently delete it. Derivative publishing also
uses RENAME_EXCL for both publication and preservation, so unsupported filesystems
can fail both operations (`DerivativeOutputPublish.swift:128–132`).

**Reproduced:** kept-name collision returns the partial with `live=false`;
advancing the sweep clock by 25 hours deletes the completed output. Preserve
completed-output state durably even if moving it fails, including across restart.
The existing kept-name-collision test stops before aging and sweeping the file.

### D3 — P1: an aliased external archive is classified as a boot-disk folder

`ArchiveVolumeProtection.swift:145–151` classifies any designation outside literal
`/Volumes/` as a boot-folder archive. Line 189 consequently skips the final UUID
check. Initialization only standardizes the selected URL
(`VideoScanModel+MasterArchive.swift:404`), and an existing alias with the expected
UUID survives mount re-resolution.

**Reproduced:** designation `/System/Volumes/Data/Volumes/FamilyArchive`, with an
archive UUID, returns `clear` for `/Volumes/FamilyArchive/loose.mov`; the supplied
UUID probe is never called. A symlink or custom mount has the same structural
problem. Ordinary files outside the archive tree can pass physical-removal
protection. Resolve boot/external placement from actual mount identity off-main;
retain external-volume protection regardless of path spelling.

### D4 — P2: per-copy Trash failures still advance the batch queue

`PruneApplyJob.swift:533–544` records `.failed` rows but finishes the job with
success. Queue handling at 684–691 then starts the next batch. Only a terminal
`.failed` drops the line, and existing error coverage exercises a startup
read-only failure. Operational failures should preserve accumulated results and
end the batch as failed. Source-confirmed; no app-host runtime reproduction.

### D5 — P2: unchecked-survivor intent is not rechecked after long verification

`VideoScanModel+PruneApply.swift:581–590` carries target/archive proof into the
final guard, not the unchecked survivors accepted during preparation. An
unchecked keeper disappearing during hashing does not stop the selected copy
being trashed. The verified archive survives, but the promised working copy does
not. Carry survivor requirements into the mutation guard; the existing
`beforeMutation` seam can reproduce this. Source-confirmed; no runtime claim.

### D6 — P2: unresolved archive identity permits catalog removal

`VideoScanModel+MasterArchive.swift:671` permits `.catalogRemoval` when the volume
verdict is `.unprovable`. After a rename/reconnect, the real archive may be at
`/Volumes/FamilyArchive 1` while its snapshot is still provisional. Non-promoted
records outside the archive tree can then be removed, purged, or tidied. Catalog
operations also lack the disk-removal path's alias UUID check. This removes
catalog state, not media bytes. Defer affected catalog mutations until identity
is resolved, while preserving the intended handling of unrelated volumes.

The older #1621 concern about a volume already offline when duplicate-plan resume
starts now has a gate at `DeleteDuplicatesJob.swift:1568`; it is not repeated as
an unresolved finding here.

## Angel S3 rules (#1638): changes required

### A1 — P1: the regex guard can freeze both validation and scoring

`ArchiveAngel/Recommend/AngelPolicyDefaults.swift:179–193` bans repeated groups,
then runs unrestricted `firstMatch` on one fixed sample. Its elapsed-time check
occurs after matching returns. Repeated atoms and character classes evade the
structural check.

This valid-shape override exceeds a two-second timeout inside validation itself:

```json
{"schemaVersion":2,"tables":{"appCacheNamePattern":"^[a1_-]*[a1_-]*[a1_-]*[a1_-]*[a1_-]*b$"}}
```

The pattern `^a*a*a*a*a*a*a*a*a*b$` is accepted in 0.00093 seconds, yet matching
twenty `a` characters plus `!` takes 0.15 seconds; thirty exceeds two seconds.
`ArchiveAngelScorer.swift:899` uses unrestricted matching in the main-actor sweep;
policy loading also happens synchronously from the main-actor facade initializer.
Both cases were reproduced with strict subprocess timeouts. Restrict expressions
to provably bounded operations or provide bounded matching. Timing one sample
after completion cannot impose an execution limit.

### A2 — P2: an optional rejection masks an offline safety floor

`ArchiveAngelRecommendations.swift:504–521` enforces safety by inspecting the
scorer's single recorded rejection. With the valid override
`{"schemaVersion":2,"recommend":{"useAngelFloors":false}}`, an offline,
30-second, three-star dated video hits `tooShort` before `volumeOffline`. The
classifier ignores that optional rejection and can classify it Ready through
the vouch/date rules. Run safety checks independently before optional floors.
Prepare independently rejects the candidate; this is a recommendation defect,
not a demonstrated archive-write bypass. Source-confirmed, not runtime-tested.

### A3 — P2: badges do not use the effective live classification

`ArchiveAngel/Facade/ArchiveAngel.swift:217–224` reads stored evidence for class
and badge, whereas `ArchiveAngel+Recommendations.swift:74–79` excludes candidates
that the current catalog refuses. A formerly Ready record can disappear from
counts/filter after set-aside or promotion but retain its Promote me badge.
The class accessor handles promoted overlays; the badge handles prepared only.
Have all consumers use one effective classification. Source-confirmed.

### A4 — P2: cached Prepare can ignore a newly chosen Keep copy

`ArchiveAngel/Prepare/ArchiveAngelJob+Evidence.swift:90` filters cached classes
before live projection. `ArchiveAngelEvidenceStore.swift:292` omits Another copy.
After a sweep marks A Ready and B Another copy, mark B Keep while A remains
Review. Before rescore, or with continuous assessment disabled, B never reaches
the live keeper chooser. A complete cached batch can still choose A. Invalidate
the selection on relevant catalog changes or reclassify affected groups before
filtering. Source-confirmed; fresh-selection tests do not cover this transition.

### A5 — P2, preexisting: the policy file cap does not bound allocation

`AngelRecommendationPolicy.swift:207,256–258` reads whole-file `Data(contentsOf:)`
before checking the new 1 MB limit. A large mistaken policy file can allocate
arbitrary memory synchronously before refusal. The S2 reader already had this
hazard; S3's cap does not fix it. Use a bounded read of at most max+1 bytes rather
than relying solely on a size check before a whole-file read. Source-confirmed.

## Archive-tab grouping (#1634–#1635): changes required

### U1 — P2: distinct recordings collapse into version chips

`ArchiveItemVersions.swift:93–97` groups on year plus normalized stem, after full
date prefixes are stripped. `1990-01-01_Birthday.mov` and
`1990-09-01_Birthday.mov` become one card. Lines 170–172 also strip any `_NN`
suffix as a presumed promote collision: `Clip_01.dv` and `Clip_02.dv` become one
card. Both were reproduced using the production grouping implementation.

Preserve distinct recording/date/camera-counter identity. Only fold when a
relationship is established; a collision-shaped name alone does not establish
one. The every-ID-appears-once sensor passes these failures because chips retain
the IDs; it does not prove that the grouping is correct.

### U2 — P2: an ambiguous version attaches to whichever year arrives first

`ArchiveItemVersions.swift:109` chooses `byStem[key].first`. With Birthday
originals in 1990 and 1991, an undated `Birthday.vs.archive.mov` attaches to 1990;
reversing input attaches it to 1991. Reproduced. Require an unambiguous parent or
leave the version independently visible. Sorting the input would merely make
the wrong inference deterministic.

## Find Original / Find Related design (#1633–#1634)

The design remains at `501916ad`. The earlier design review still applies:

- Sampled content hashes/partial MD5 nominate candidates; they cannot authorize
  shared full fingerprints or an Identical verdict. Define verified identity,
  `p:` to `h:` promotion, and conflict handling.
- Preserve immediate operation parents and their trim offsets. Discovered
  ancestry needs typed relationships and multiple source ranges for compilations.
- Containment alone cannot identify derivation direction. A multi-date
  compilation cannot inherit one source's capture date.
- Matching audio means shared audio; a reused soundtrack does not prove an event.
- Provenance and correction/retraction belong in the first phase that writes
  dates/relationships, not a later learning phase.
- Mounted and awake are different states; the indexing drive policy must say
  whether waking mounted drives is allowed.

### Minimal counter-proposal

Start with metadata candidate retrieval, explicit evidence/reasons, side-by-side
inspection, and recorded human decisions. Keep user judgments outside the
disposable fingerprint cache. Treat Find Original (provenance) and Find Similar
(semantic retrieval) as different questions in the data model, even if the UI
shares a sheet. Do not infer lineage or propagate dates from semantic similarity.

Then spike audio and visual segment retrieval on a small labeled corpus before
indexing 9.6 TB: re-encodes, trims, long uninterrupted takes, compilations,
speech/room audio, reused music, and same scene/different camera. Measure retrieval
recall, false matches, alignment error, read/decode time, and index memory.
Accelerated embeddings are worth testing for semantic candidate retrieval;
temporal correspondence still supplies footage evidence. Compare them against
the simpler existing perceptual baseline before selecting a dependency/model.
Transcripts can later nominate shared topics without establishing recording
identity. Defer learned weights until labels distinguish identity, derivation,
shared event, and semantic similarity, and a held-out evaluation supports a change.

Chromaprint itself describes a near-identical-audio target rather than general
audio similarity: https://github.com/acoustid/chromaprint . Apple's ShazamKit
sample demonstrates local custom-catalog synchronization, not this archive's
retrieval quality: https://developer.apple.com/videos/play/wwdc2021/10045/ .
