## Findings

1. **P1 — stale archive evidence inflates the deletion tier.** `DeleteDuplicatesPlan.swift:148–162` counts an archive from its present size and its previously recorded digest, without matching a current ctime-bearing identity to that digest. Ordinary sibling copies do require such a match. Same-sized corruption/replacement of an archive therefore still counts: keeper + valid sibling + corrupt archive authorizes permanent removal although only two verified copies remain, which should require Trash. Require current, identity-bound evidence for archive candidates as well as siblings. Add a regression with a same-size archive rewrite and assert the lower tier.

2. **P1 — a forced stop after “finish this file” can still launch deletion.** `DeleteDuplicatesJob.swift:425` sets `finishInFlightForQuit = true`; `stopForQuit` (409–415) and `cancel` (391–402) never clear it. The deadline handler (1478–1489) calls `stopForQuit`, but a ticket-save await has no disk worker to cancel. On return, the still-true flag bypasses both the release branch (811–819) and cancellation of the new worker (989). A timeout or explicit Stop must revoke finish permission. Add a deterministic finish-then-stop regression at the saved-ticket boundary.

3. **P1 — an unrecovered quarantine becomes undiscoverable.** `DeleteDuplicatesJob.swift:723–746` sets `finishedAt` before saving the plan with stranded rows. The file and plan remain physically present, but `DeleteDuplicatesPlan.isResumable` (423) requires an unfinished plan with unsettled rows; `unfinishedPlans` (649–660) consequently excludes it. Restoration failures also settle the row as refused. Resolve an occupied destination after a failed recovery and relaunch: no recovery offer returns. Preserve a discoverable recovery state, distinct from permission to delete. The existing stranded test checks only filesystem placement and the console message, not subsequent discovery/retry.

4. **P1 — retained-copy evidence can expire while the quarantine ticket is saved.** `DeleteDuplicatesJob.swift:793–803` chooses the tier then awaits persistence. Deletion at 824–825 checks only target and keeper identities (`SignatureVerification.swift:692–695`), never the other copies counted toward the tier. Remove or rewrite a counted sibling while persistence is pending: permanent removal still proceeds using the old count. Revalidate the identities of the retained copies at the mutation boundary and downgrade/refuse when the required count no longer holds. The existing `testHookAfterQuarantineSaved` can deterministically exercise this regression.
