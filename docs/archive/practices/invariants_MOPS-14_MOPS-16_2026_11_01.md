## MediaOps, MOPS-14

14. **MOPS-14** Audit Catalog tier 0 (`CatalogAuditJob`, design: docs/archive/design/catalog_status_freshness_2026_10_16.md §6) only STATS: the first pass is one `stat(2)` per media path; nothing on media is opened, moved, renamed, deleted or written, and the archive volume is never touched. THE ONE DECLARED EXCEPTION TO "NOTHING OPENED" (codex r2 2026-10-16 F2): the audit opens a DIRECTORY handle — read-only (`open` / `openat` with `O_RDONLY | O_DIRECTORY | O_NOFOLLOW | O_CLOEXEC`), never a media file, never for writing — and reads through it (`fstatfs` + the volume's persistent UUID via `fgetattrlist ATTR_VOL_UUID` (`VolumeIdentity`), `fstatat` with `AT_SYMLINK_NOFOLLOW`, `fstat`; plus `lstat` on pathname components for the two D6 checks below); these calls live in `CatalogAuditPlan.swift` (`CatalogAuditDirectoryWalk`) and nowhere else in the audit, every handle is closed on every path. The handle is opened twice per row at most: in the first pass for a file the stat found PRESENT (one handle per folder, the identity through it, each name through it — the where-seen STAMP), and at the mark for a gone answer. THE ONE PROOF RULE (codex r3 2026-10-16 F1, D5 — supersedes the r2 lane-root identity and the "/" stub rule, both removed): a row is marked gone only on evidence read at the moment of marking, THROUGH THAT HANDLE, in a folder on the volume the file was LAST SEEN on — the handle's volume UUID equals the row's `VideoRecord.auditSeenOn` stamp (volume UUID, what was mounted there, when — and, D8, the PHYSICAL DEVICE KEY `AuditSeenOn.deviceKey`: `DuplicateDrives.physicalDeviceKey`, the same DiskArbitration device-path digest the Delete Duplicates two-drives rule compares, asked for the handle's `f_mntfromname`; nil for a network share or a disk image; a LOCAL device DiskArbitration cannot describe gets NO stamp at all — codex r5 2026-10-16 P1 — because a key-less stamp would later prove by volume UUID alone), which the audit itself writes for every file it finds (present, changed, came back) and which clone, rescan preservation and the catalog file carry. No stamp → `neverSeenByAnAudit` ("not at its path, and no audit has seen it before — Fix Links decides"): counted as needs-a-decision, NEVER marked. A different volume → "could not check — the folder is on a different volume than the file was last seen on (drive not connected?)": an unmounted drive's stub folder, a nested volume that left (its stub belongs to the outer volume), a relocated home, a volume with no UUID — all refused by the one rule, nothing inferred from the lane root or from what a folder holds. THE DEVICE (codex r4 2026-10-16 F1, D8): a stamp that carries a device key is held to it — the handle's device key must equal it; the same volume UUID on ANOTHER drive (a clone, a restored image, mounted at the path while the original is disconnected), or on a drive DiskArbitration cannot describe → "could not check — a clone? not marked". A stamp WITHOUT a device key (a share, a disk image, an older stamp) proves by volume UUID alone: a share's clone is the share. The one DiskArbitration call lives in `DuplicateDrives` (DeleteDuplicatesDrives.swift), never in an audit source. The lane root's mount check (kernel mount table, read fresh, no cache, after the stat) is only the cheap "not asked" skip. The chunk's ENOENT is a first pass that decides nothing. THE WALK (r2 F2, r3 F2 = D6): first every EXISTING component of the path, lexically, with `lstat` — a symlink ANYWHERE (an intermediate one too, `/var` → `/private/var`; test sandboxes use a realpath'd root) → "could not check — a link in the path, not provable"; then open the nearest existing ancestor folder (walking up by opening, O_NOFOLLOW on each step's last component); then — D9 (codex r4 F2), because O_NOFOLLOW guards only the LAST component of the pathname the open was given — the lexical `lstat` walk AGAIN after the open and the handle must name its path (`fstat(fd)` dev+ino == `lstat(path)` dev+ino, a directory) before anything is read through it, in the proof AND in the first pass's stamp acquisition (`seenOn`: a link substituted for an intermediate folder between the walk and the open, or the folder replaced between the open and the name read → NO stamp, the row's old stamp untouched); then `openat` each remaining folder one at a time (closing the previous handle), `fstatat` the name; after an ENOENT / ENOTDIR on a folder or the name the handle must STILL be the directory its pathname names (`fstat(fd)` dev+ino == `lstat(path)` dev+ino, a directory) → else "could not check — the folder changed under the audit"; a symlink in the remainder or where the walk lands (ELOOP, or — Darwin reads a symlink refused by `O_NOFOLLOW | O_DIRECTORY` as ENOTDIR — a folder that would not open and that `fstatat` link-not-followed shows to be a link) → a link in the path; a file where a folder was → could not check; any other errno → could not check; present → present (a link where a file was is "not a regular file", never gone). Declared residual: a file arriving after the observation, or a folder replaced and replaced BACK between two syscalls (two renames by an outside actor inside that window) — the next run restores it. WHAT IT WRITES: the removal marker of a catalog row — `stampRemoval(.missing, reason .missingAtAudit)` for a live, non-archived (read from the LIVE record) row proven gone as above, and `clearRemoval` (which validates the file is back first) for a Missing row whose file is at its path — both through `VideoScanModel.applyCatalogAudit`, which is compare-and-set on the row's id AND a snapshot of the fields that matter as planned (path, size, marker, lifecycle stage, archive stage and fixity presence, derivation kind, supersession, hash time, mtime, the stamp — r2 F3, r3 D5); the where-seen stamp (`auditSeenOn`, in exactly one place in the model half; not a mark: no undo bookkeeping, no revision, flushed with the marks on the 60 s clock, at lane end and at run end — never a save per row; a save that is not acknowledged simply loses the stamps; D10: a stamp is "this path's folder, on this volume" — ANY change of `VideoRecord.fullPath` (Relocate, a source-side move, a rename, a volume-rename migration) clears it in the one setter — codex r5 P2 — and the next audit stamps the new place and marks nothing there); catalog saves; log lines through one sink; and `catalog-audit.json` beside catalog.json through `AtomicFilePublish`. WHAT IT NEVER DOES: mark a row whose root is not mounted (not asked); mark a row no audit has seen; mark on any errno but ENOENT / ENOTDIR or on a path that is no longer a regular file (could not check); mark a "changed" row (size differs — reported) or an archived copy whose file is gone (reported); delete a row; leave an unsaved mark — a save that is not acknowledged undoes that batch's marks BY VALUE AND REVISION on the current row instance (`revertRemoval`, r2 F4: `VideoRecord.removalRevision` is bumped ONLY by the engine — `stampRemoval` / `clearRemoval` / `revertRemoval` — when the marker's value changes; each audit mark records the revision its write produced; the undo requires the row to still carry exactly the audit's marker AT that revision, so an equal value written since by another door — nil → Trash → Put Back → Restore → nil, or an identical marker reinstated — has a higher revision and is left alone, "changed by another door"; only the marker and the mirrors the write itself moved go back; accepted: an identical re-stamp by another door leaves the revision unchanged, so the rollback can clear that identical marker — it is the audit's own value) and fails the run — failed > stopped > completed, so Stop followed by an unacknowledged save is "failed" (CLI exit 1, run marker failed, row "Failed — marks undone"), never "stopped"; a stopped run says "partial". Rescan preservation carries `removalRevision` and `auditSeenOn` (r3 F3 = D7: a row with removal history alone stays in the rescan map — `carriesRemovalHistory`). The headless `--audit-catalog` refuses when the VideoScan app is open (one catalog writer) and on a viewer-role Mac. `CatalogAuditJobSensorTests` reads the sources (the second look before the one `stampRemoval`, against the live record's stamp; the one-rule guard; the two D6 checks; the D9 post-open binding in the proof and in `seenOn`; the D8 device comparison; no DiskArbitration call in any audit source; no `await` in the model half; no object memento; the handle calls in the plan file only; no superseded rule left; no write / rename / unlink / open-for-writing anywhere in the audit); `OneEngineSensorTests` pins the one bumper of the revision; `CatalogAuditProveAtTheMarkTests` and `CatalogAuditRound2Tests` pin each case on the real filesystem.

## MediaOps, MOPS-16

16. **MOPS-16** Import to SQLite (`ImportToSQLiteJob`, design: docs/archive/design/catalog_sqlite_migration_2026_10_16.md §10c "app wiring"; ONE ACTION VERB, Rick 2026-10-17) — ONE WRITER, ONE GENERATION: from the moment the pre-flight passes until the Core importer returns, every write to catalog.json is HELD under an OWNER TOKEN (`CatalogStore.holdWrites(reason:owner:)` / `releaseWriteHold`, checked in `writePrecondition` before the lock). Taking the hold is an ATOMIC ADMISSION BOUNDARY (codex 2026-10-17 P2): `holdWrites` (async) sets the hold on the main actor, then waits behind `writeQueue` (serial with saves) and for the main-actor completion of every save admitted before it, so when it returns nothing admitted earlier is outstanding; the START line's generation is read after that drain. The drain is BOUNDED (codex 2026-10-17 round 2 P2): `holdWrites(reason:owner:within:)` returns `.writerStalled(heldSaves:)` when an admitted save does not land within `CatalogStore.holdDrainDeadline` (60 s), the hold already given back; the job then refuses before phase 1 with "a catalog save did not finish within 60 s — try again" (a save refused meanwhile is caught up). `hasUnsavedChanges` counts acknowledged saves in flight too. While held: `saveNow`, `scheduleSave` → `saveAsync` and `saveAcknowledged` all refuse with `.heldByJob(reason)` (journalled like every refusal) — EXCEPT an acknowledged save that presents the holder's token (`saveAcknowledged(records:as:)`; `CatalogWriteHoldOwner`, a fresh token per job; any other token or none is held). The held saves are counted and become ONE catch-up `saveCatalogDebounced()` when the job lets go, so a change made during the run is delayed, never lost. QUIT during a run (codex 2026-10-17 P1): the app's quit path (`applicationShouldTerminate`, `.terminateLater`, both file-operation paths) Stops the job, awaits its end — bounded, `ImportToSQLiteQuit.deadline` = 30 s; the importer rolls back and the job releases its hold — then makes the DURABLE `saveNow` of the held edits before replying; past the bound the hold is released by force and the edits are saved anyway. THE COMMIT FENCE (round 2 P1) is by construction: a commit-mode importer never writes `catalog.sqlite` — it writes a STAGING folder beside it (`catalog.sqlite.importing-<runID>/`: its own database, WAL, -shm and high-water witnesses) and, only when `.imported`, closed, reopened `.readWrite` and verified ok, PUBLISHES through a gate Stop closes (`ImportStopFlag.claimPublish` / `raise` under one lock, the importer's `publishPermit`): RENAME_EXCL of the companions (catalog.highwater, catalog.highwater.log, -wal, -shm) first and the database LAST, every target name checked absent first, a failed rename putting back what moved. So a COMMIT that completes after a forced release lands in staging; the outcome is `stopped`, catalog.sqlite never appears, and the quit line says which happened (gate held, or publish already begun). Stopped / rolled-back / failed / abandoned runs leave only staging; the next commit run MOVES leftovers (every `catalog.sqlite.importing-*`, and companions beside no catalog.sqlite) into one `catalog.sqlite.import-aside-<stamp>/` folder before it starts — nothing is deleted. An existing catalog.sqlite (even empty) refuses before anything is written. The WAL travels with the database because the store's close does not fold it in (GRDB closes the writer before its read-only readers). THE SAVE AT QUIT IS CHECKED (round 2 P1/P2): the quit first asks the store whether every admitted save drains within `ImportToSQLiteQuit.writerDeadline` (`waitForWriterToDrain`, awaited — the main thread is free); a writer that does not is STALLED and the synchronous save is skipped (it would block the main thread on `writeQueue.sync`); a stalled writer or a save that fails is followed by a RECOVERY COPY — the in-memory catalog in the store's own payload/encoder, published with AtomicFilePublish (`.fullFsync`) off `writeQueue`, bounded, as `catalog.recovery-<stamp>.json` beside catalog.json (START/OUTCOME through `catalogQuitNote`); `settleAndSave` returns `.saved` / `.recoveryCopy(url)` / `.unsaved(words, changes)` and the delegate replies with it: `.unsaved` raises an alert with the store's words, "Keep VideoScan open" (default → `.terminateCancel`, nothing shut down) or "Quit and lose N unsaved change(s)". `applicationWillTerminate` Stops a running import, releases a hold still up, then makes the same CHECKED save (`CatalogQuitRecovery.saveAtTermination`, its waits bounded by semaphores) and logs the branch. The next launch says when a recovery copy is beside the catalog (console + catalog.log); nothing merges it. The quit lines go through the one sink. Inside the hold the job runs THREE PHASES in order: (1) Audit Catalog — the existing `CatalogAuditJob`, not added to the center, its saves presenting the token (`writeHoldOwner`): its where-seen stamps and marks are evidence the importer checks (N1); when it ends the store's generation is G; (2) Verify Catalog — the existing `VerifyCatalogJob`, made only after the audit's finishing second + 1.5 s (`ImportToSQLiteTiming.verifyStartDelay`: the gate refuses an audit that finished in the second Verify started), the wall clock RE-READ after every wait and waited out again on a backward step, bounded (`waitForVerifyStart`, `verifyWaitRounds`; a clock that keeps stepping back refuses with words — codex 2026-10-17 P3); it snapshots catalog.json AS THE AUDIT SAVED IT — decoded read-only off the main actor with `load()`'s own decoder (`CatalogStore.decodeCatalogFile`), refused unless it carries exactly G (`VerifyCatalogJob.snapshotSource = .auditedFile(generation:)`) — never the in-memory rows, so an edit made after the audit's save cannot be certified as G (codex 2026-10-17 P2; the standalone Verify Catalog still snapshots the live rows); (3) the import — after checking catalog.json's header is still at G, the Core importer. A phase that cannot complete stops the job with its own words ("the audit could not complete: …"), nothing is imported, the hold is released. While an import is active the standalone Audit Catalog and Verify Catalog starts refuse ("Import to SQLite is running and runs its own …"). The job READS the catalog folder; besides what its audit (MOPS-14) and Verify (MOPS-15) write, it WRITES at most two things: `catalog.sqlite` beside the catalog (commit mode, by publishing its staging folder as above — refused before any work when it already exists; the importer's own existing-target and target-empty checks stand behind that; a staging folder or an aside folder of leftovers may remain beside it) and the dry-run marker `import-dryrun.json` (`ImportDryRunMarker`, `AtomicFilePublish`, MOPS-13's shape: a missing, damaged or other-build marker only disables a menu item). A DRY RUN writes no database beside the catalog: the importer runs the identical flow (gate, one transaction, rows, sidecars, comparator) against a database in a scratch folder it owns under the temporary directory and rolls the transaction back by design (`.dryRunPassed`), then removes that folder — the one deletion in this lane, scratch only, never a catalog or media file. REFUSE BEFORE ANY WORK (`ImportToSQLitePreflight`, pure, every refusal listed with its words): unsaved catalog changes; another MFO job running; `catalog.sqlite` already there (commit). Open Delete Duplicates plans and Archive Angel batches refuse through the importer's gate. The JSON catalog is never moved, renamed or deleted by this lane, and written only by its own audit's saves — the cutover (F′) is a separate, later act. Stop = forwarded to the phase job in flight (the audit saves what it marked; Verify ends after its tier) and the importer's `stopRequested`, asked before the target opens and at each phase boundary of its one transaction: the row ends Stopped (never Done), nothing imported; Pause is not offered. The real import is offered in the Catalog menu ONLY when a dry run passed ON THIS BUILD (`ImportBuildIdentity.current` = CFBundleVersion + the image's Mach-O UUID, recorded in the marker beside the catalog, never UserDefaults; the generation no longer gates — the real run re-proves audit + verify + gate + comparator) and after a sheet showing the last dry run's line and saying so, and "the JSON catalog stays as it is; nothing is deleted". START / the phase lines / the importer's lines / OUTCOME go through the one sink (`importToSQLiteNote`: console + catalog.log, videoscan.log, the unified log); the phase jobs log through their own sinks. `ImportToSQLiteSensorTests` reads the sources (hold with the token before the three phases, release after, no catalog save in the job, the audit's save presents the token, only `saveAcknowledged` presents one, the precondition checks the hold before the lock) and the quit wiring (settle on both `.terminateLater` paths and REPLY with its answer; willTerminate cancels, releases, then the checked save; wait → forced release → drain check → save in that order; the job passes the publish gate), `CatalogImporterStagingTests` (Core) pin the late COMMIT staying in staging, the next import moving leftovers aside byte-for-byte, an existing target refusing and the published set opening read-write and verifying, `ImportToSQLiteQuitPathTests` pin the late-COMMIT quit end to end, a refused save leaving a recovery copy with the edit, both failing → `.terminateCancel`, willTerminate's checked save, the launch notice, the bounded hold and the job's refusal on a stalled writer, and the quit skipping its synchronous save behind one, and `ImportToSQLiteJobTests` / `ImportToSQLiteHoldTests` / `ImportToSQLitePreflightTests` pin an edit made during a held run in catalog.json after a quit (job ended, and past the bound), Verify's report counting the audited file's rows not an in-memory addition, a save admitted before the hold landing before it (store and job) and an acknowledged save in flight counted unsaved, a backward clock step waited out again (and a clock that keeps stepping back refused), the three phases in order at one generation, a background save in EACH phase held with the generation and the file's hash moved only by the audit's own save, the owner's save passing and another token held, each refusal, a phase that cannot complete, Stop in each phase → stopped with nothing imported and the hold released, and a real import enabled by a this-build dry run at an older generation.
