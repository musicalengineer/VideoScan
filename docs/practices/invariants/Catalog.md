# Catalog file (catalog.json): versions, unknown keys, newer catalogs

Rick, 2026-10-02 (GH #167): "make sure we don't run into forward/backward
compat issues, so we don't need to be psychotic about it, just polite."

## Invariants
1. **CAT-1** Nothing a newer build wrote is silently lost. Every JSON key this build does not know — at the top level of catalog.json or inside a record, nested values included — is kept with its exact value (`unknownFields`; numbers see "Known and accepted") and written back on every save path (live save, async, acknowledged, safety snapshots), carried through a rescan's record replacement, and merged forward by the live reload.
2. **CAT-2** An unknown key never overrides a known field. Capture skips every key in `VideoRecord.persistedKeyNames` / `CatalogSnapshot.topLevelKeyNames`; emit skips them again, so a known field is only ever written from its typed property and the top-level `version` / `generation` stamps stay first and single.
3. **CAT-3** A catalog written by a newer build (its `version` > `CatalogSnapshot.currentVersion`) is read-only, never an error and never a downgrade: its records are shown for browsing, catalog.json and catalog.json.prev get zero bytes (no rotation), every save and snapshot path refuses, the app shows the "saving is paused" banner and reads as read-only, and background jobs that would save are held and say so (once). This holds when the newer file is found at load, when it cannot even be decoded (no fallback to .prev with writes on), and when it appears mid-session (the write path probes the version when the save is queued AND again on the write queue immediately before the bytes land — `CatalogWriteGate`, codex cycle #28 #1 — and the store's one-shot `onNewerCatalogLatched` flips the model's banner and `isReadOnly` on that same refused save). The version probe reads only the TOP-LEVEL `version` (a record's own `version` key is never mistaken for it — `CatalogHeaderScanner`, codex #2), and it reads the WHOLE top-level object in one streaming pass (codex cycle #30 R1): no head/tail window, no stopping once a stamp is in hand — a later duplicate stamp, a truncation or trailing bytes all change the answer. Duplicate top-level stamps keep the HIGHER value (readers disagree: Foundation keeps the first, python's json the last; max refuses either way). Its answer is THREE-WAY (codex cycle #29 F1): `.version(n)` and `.confirmedAbsent` BOTH require one complete, well-formed object (`.confirmedAbsent` = no `version` key at all — a genuine v0 catalog, writable), and everything else is `.unknown` (a leading UTF-8 BOM is skipped as Foundation skips it; array root, UTF-16, garbage, truncated or unterminated, mismatched delimiters, bytes after the object, any top-level `version` whose value is not a canonical integer, an unopenable file). "Well-formed" means exactly what the scanner validates (QA r4, `CatalogScannerNonCanonicalStampTests`): bracket KINDS match (`]` cannot close `{`); string state (quotes, backslash escapes); no raw byte < 0x20 anywhere except the four JSON whitespace bytes between tokens (a raw control byte inside a string is illegal JSON too); stamps are CANONICAL non-negative integers (no sign, no leading zero, no fraction, no exponent); nesting no deeper than 256 containers (`CatalogHeaderScanner.maxContainerDepth` — the stack is bounded, a file of ten million `[` aborts). It is NOT a full JSON validator: a missing comma or colon, a bare word, a stray high byte outside a string are tolerated — none can change where a top-level `version` sits or what its integer is. A file the probe cannot OPEN is two different things (QA r4 item 3): a permanent errno (EACCES, EISDIR…) is `.unknown` → session hold, as above; a TRANSIENT errno (EMFILE/ENFILE during a media scan, EINTR, EAGAIN), still failing after one retry 50 ms later, is `.unavailable` → THIS write is refused with `CatalogWriteError.catalogUnavailable` ("couldn't check the catalog file right now — try again"), journalled, and the session is NOT held; a landed save's completion then skips the sidecar and the observer once; `load()` on such a launch shows the decoded records and writes no sibling (no bootstrap, no sidecar bump, no .prev rotation) without holding — an UNDECODABLE primary that also cannot be opened holds (nothing can be verified). `CatalogWriteHold.from(.unavailable)` is nevertheless `.versionUnknown`, so a gate that forgot to check `.unavailable` first would hold — the safe side (`CatalogProbeOpenFailureTests`). **Unknown is never "old"**: every gate holds on it for the session (`CatalogWriteHold.versionUnknown`), with its own words (`CatalogStore.unreadableCatalogNotice` — "could not be read … restore catalog.json from catalog.json.prev or a backup", never "newer"). The O(file) pass is bounded by a verdict CACHE, not by the hold (codex cycle #30 R4): one verdict per path, keyed by the file's device + inode + size + mtime + ctime (`CatalogHeaderScanner.FileKey`, fstat(2) on the handle that is then read), and every write this process verifies seeds the cache with the verdict of the bytes it proved on disk (the key is taken from the handle the read-back SHA-256 hashed) — so a probe costs one open + stat unless the file CHANGED (`CatalogProbeCacheTests`: 63 MB / 200k records, version mid-file — first probe ≤ 2 s off-main, repeated ≤ 5 ms, one pass; stale-generation refusals and a v0 load + save scan once). A corrupt catalog.json therefore pauses saving instead of being overwritten from .prev; .prev is still shown for browsing — this includes a catalog.json left malformed by THIS process's own write when its read-back verification failed (surfaced by R1; `CatalogVerificationFailureTests`; Rick to rule whether that case should stay replaceable). `load()` writes nothing (not even the first-run `catalog.generation.max` bootstrap, nor a reconcile bump) until the full decode has said the file is not newer, nothing at all while held, and — decision (i) of codex cycle #30 R2 — it adopts the PROBE's hold even when Foundation decodes the file (UTF-16 BOM, an integral-but-not-integer spelling, a duplicate stamp the probe reads higher than the decoder): the probe is the one gate for load and save alike, the decode supplies the records to browse and nothing else (`lastLoadOutcome == .openedReadOnlyVersionUnknown`, `CatalogLoadHonoursUnknownVerdictTests`). The write-queue gate re-reads the latch mirror AFTER its on-disk probe and before it answers, so a latch raised during a long probe is honoured (codex cycle #29 F2). Writers that do not take the write lock — safety snapshots and the notes-repair backup/marker — probe the primary themselves before touching a sibling (`refuseIfNewerCatalogOnDisk`, codex #5), and deferred sibling writes re-check at their own mutation boundary (codex cycle #29 F4): a landed save's completion (`finishWrite`) probes ONCE and uses the answer for both `catalog.generation.max` and the observer notification — `catalogStoreDidWrite` (CatalogSync's manifest.sha256 refresh, a deferred sibling write of the same class) is fired from that one place only, after the lock is released, and not for a save whose primary has since been replaced (codex cycle #30 R3, `CatalogObserverGatedByHoldTests` incl. a source sensor on the single call site); the notes repair re-checks after its records scan and again right before its marker (clean AND dirty plans, `CatalogCycle30PredictedSurvivorTests`). The live reload while paused READS: it decodes the newer file and merges what it shows (dossier fields, new records, unknown keys) into memory so browsing stays current; it WRITES nothing — no generation adoption, no sidecar (`CatalogReadOnlyLiveReloadTickTests`). While paused, the ONLY files that may change beside catalog.json are the refusal journal (`catalog-write-errors.jsonl`) and the advisory `catalog.lock`; no .prev rotation, no `catalog.generation.max` bump, no pre-* snapshot, no notes-repair marker (pinned by `CatalogNewerVersionNoWritePathTests`).
4. **CAT-4** When to bump `CatalogSnapshot.currentVersion`: ONLY when an existing field's MEANING or TYPE changes, or a field is removed or renamed. ADDING a field never needs a bump — CAT-1 carries it through every v7+ build untouched. The key-snapshot sensor (CatalogVersioningTests, `CatalogKeySnapshotSensorTests`) fails on any key change so the addition is a deliberate one-line edit to the snapshot, not a bump.
5. **CAT-5** Every older catalog (no version key, v1–v6) loads and upgrades in place on the next save, keeping its data; the original bytes are in catalog.json.prev after the upgrade, and a second load → save does not re-migrate (fixtures in `CatalogOlderVersionUpgradeTests`).
6. **CAT-6** Preservation is cheap: records with no unknown keys allocate nothing and encode byte-identically to before (the byte-identity goldens in CatalogStoreAsyncSaveTests); 100k records that all carry unknown keys stay inside the existing 20 s save / load budgets (Debug).
7. **CAT-7** Exactly five CatalogStore entry points reach the byte writer (`encodeAndWrite`): saveNow, saveAcknowledged, saveAsync (via `writePrecondition`) and writeSnapshot / writeSnapshotAsync (via `refuseIfNewerCatalogOnDisk`). The byte writer itself takes a REQUIRED `CatalogWriteGate` and re-checks the latch and the on-disk version AFTER encoding and BEFORE writing (after, so the check is as late as possible; the sensor pins both sides — a check moved before the encode would widen the window by the whole encode time). A new write path must pass the latch; the source sensor `writeEntryPointsAreLatched` counts the call sites and pins `payload.encoded(` < `gate.writeHold()` < `data.write`.

## Known and accepted (do not report)
- v7 is the first version that preserves unknown keys. Builds from before it (before 2026-10-02) still strip keys they do not know; the v6 → v7 bump is what makes the ones that check the version refuse to save a v7 catalog.
- Builds that predate the version check itself (before 2026-05-26) cannot be protected by any bump: they read and rewrite catalog.json without looking at `version`.
- Builds from 2026-05-26 to 2026-08-14 (before the write latch, dc62babf / codex #377) refuse to LOAD a newer catalog but do not latch writes, so their quit-time save can replace a v7 catalog with a near-empty one. Do not run a build from that window against a v7 catalog (flagged to Rick with the v7 bump, GH #167).
- Numbers inside unknown values keep their exact VALUE (codex review 2026-10-02 #4 and cycle #29 F3; `CatalogJSONValueExactNumberTests`, `CatalogUnknownNumberExactnessTests`): the literal is read as a base-10 Decimal first (exact to 38 significant digits), and Int64 / UInt64 are chosen only when they EQUAL that reading — so `1.0000000000000001` (which Foundation's integer path would round through Double to 1) stays a Decimal; Double is used only for what Decimal cannot hold (huge/tiny exponents, which only a Double writes). The SPELLING is JSONEncoder's, so `1e3` comes back as `1000` and `1.0` as `1` — same value; canonically spelled numbers are byte-identical. The complete remaining-loss statement: (a) exponent-form literals come back in JSONEncoder's spelling, value exact; (b) a literal with more than 38 significant digits keeps 38 (no Swift numeric type can write one). Nothing else is lost or rounded.
- Unknown keys are carried, not interpreted: a rescan keeps a newer build's per-record keys even if that build would have re-derived them from the file. Keeping stale data beats losing it; the newer build rewrites its own keys.
- Bundle import, catalog import and other paths that BUILD new records from foreign data are not in scope; they create records rather than round-trip the user's catalog.
