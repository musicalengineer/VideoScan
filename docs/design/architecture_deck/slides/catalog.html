The catalog database: one SQLite file, one writer

Why SQLite

  • One file, transactional, WAL: a crash loses nothing committed
  • The database refuses invalid writes itself: constraints and triggers carry the rules (append-only history, the veto)
  • Scripts and the helper read it with a read-only open; one committer writes
  • Copy with .backup, never cp; additive migrations Rick approves (schema 14 today)
  • Searchable (FTS), backed up, fixity-checked, rows never deleted

What it holds, by kind (schema 14, 64 tables)

Identity

content (SHA-256), files and paths, volumes, generations

Rick’s decisions

dates, places, stars, notes, people tags, events, roles, archive state

Machine observations

captions, transcripts, inferred dates, prints, era and OCR assertions, each with who-made-it and evidence

Bookkeeping and search

ledger, audits, jobs, quarantine, full-text index

App committer

catalog.sqlite

read-only: helper, scripts, viewer Macs

.backup copies · sealed viewer snapshot · Verify Catalog tiers

Background observations travel as journal lines; the app applies them through the same door, in batches, idempotently. A decision always outranks an observation.
