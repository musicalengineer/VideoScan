## Audit — what already exists

### 1. Person-tag schema

`VideoRecord` already has TWO confidence tiers, both populated automatically
by Find Person:

| field | populated by | semantics today |
|---|---|---|
| `detectedPeople: [String]` | scan loop, ≤ `strongCutoff` distance | "confirmed match" by the engine |
| `suspectedPeople: [String]` | scan loop, between `strongCutoff` and `threshold` | "borderline" |

What's **missing** is a third source-of-truth tier:

| proposed | who sets it | semantics |
|---|---|---|
| **`confirmedByUserPeople: [String]`** | Rick clicks "this is Donna" in the UI | Ground truth. Higher confidence than detectedPeople. Never overwritten by the scan loop. |

Note the parallel with `MediaDisposition` (`Models.swift:673`):
`.unreviewed` / `.suspectedJunk` / `.confirmedJunk` mirrors the exact pattern
Rick wants: a coarse auto-flag, then a manual confirmation step. We'd
introduce a `.suspectedFamily` / `.confirmedFamily` tag-source enum (or
equivalent per-name field) for people.

**No UI today edits detectedPeople from a record inspector.** `InspectorPanel`
exists at `CatalogHelpers.swift:1537` and renders the record's fields but
doesn't include a "confirm / refute / add person" affordance.

### 2. Metadata search

There are actually TWO matchers in `CatalogQueries.swift`, and the gap is
not where I first thought.

**(a) Narrow matcher** `pfRecordFilenameOrPersonMatch` (line 149) —
searches filename + `detectedPeople` + `suspectedPeople`. This is what
the Catalog tab calls today (`CatalogHelpers.swift:517`). Intentionally
narrow — there's a design comment at line 144-147 explaining why:

> "Path, directory, codec, notes, etc. are intentionally NOT searched
> here … those live in the universal search (pfRecordMatchesQuery)
> which is too broad for the always-on catalog search bar. Typing 'matt'
> should find files named *matt* and files tagged with Matt, not every
> file in a 'Matthew' directory."

**(b) Universal matcher** `pfRecordMatchesQuery` (line 122) — already
tokenizes AND-of-terms, supports year-range tokens, and searches:
filename, fullPath, directory, detectedPeople, suspectedPeople,
**sceneCaptions[*].text**, **audioTranscript**, avidClipName,
videoCodec, audioCodec, lifecycleStage, archiveStage, notes. **Fully
unit-tested** (`AudioTranscriberTests.swift` lines 343-382;
`CatalogQueriesTests.swift` lines 125+).

**But unwired from any UI** — only callers are tests. The Catalog tab
never invokes it.

So the actual gap is not predicate code (it exists). It's a **UI scope
decision** about what the Catalog search bar should do. Three options:

| option | effect | downside |
|---|---|---|
| **A. Wholesale-swap** Catalog tab to `pfRecordMatchesQuery` | Captions, transcripts, paths, codecs all searchable from the one bar | Re-introduces the "matt → /Matthew/* directory noise" the original author wanted to avoid |
| **B. Add scope toggle** ("Files + tags" / "All metadata") next to search bar | Preserves the narrow default for "find me Matt"; the broader mode is opt-in | Adds a control to the bar; saved preference becomes new state to manage |
| **C. Extend narrow matcher** to include `sceneCaptions[*].text` + `audioTranscript` only, leaving path/codec out | Captions + transcripts join filenames + people tags as "things you can find with one click"; no path-noise re-introduction | Two predicates that are 80% the same; possible duplication drift |

I'd vote **C** — captions and transcripts are *semantic content tags*
in spirit (about what's in the video) and belong with people tags, not
with location metadata. **C is also still a ~10-line change with tests.**

If Rick wants the full universal-matcher behaviour for ad-hoc
debugging, **B** layered on top later is also cheap.

### 3. Captioning pipeline

Wired and operational:

- `CaptionOrchestrator` (`CaptionOrchestrator.swift:124`) drives the
  per-target captioning job
- `MLXVLMCaptionRunner` (`CaptionRunner.swift`) runs Qwen2.5-VL-3B-4bit
  via mlx-swift's MLXVLM
- Idempotent — skips records whose `sceneCaptionModel` matches the
  current engine unless `force: true`
- Writes captions to `record.sceneCaptions`, model to
  `record.sceneCaptionModel`, time to `record.sceneCaptionsAt`

**Yes, Qwen is wired.** It's just never been run across Rick's actual
catalog — `0 of 13,570 records` have `sceneCaptions` populated. The
machinery exists; the trigger has never been pulled.

`startCaptioning(target:model:)` takes a `CatalogScanTarget` — a single
volume / folder. There is no "caption all cataloged media regardless of
which volume they live on" loop today. Same shape as the Find Person ↔
all-cataloged-media gap.

### 4. Catalog-wide scan

`scanAllVideos` (`PersonFinderModel+JobLifecycle.swift:590`) exists but
**operates on a single search target** — same scope-limitation as
captioning. The "scan everything in the catalog regardless of which
volume" workflow would be a new entry point that iterates `model.records`
filtered by some predicate (e.g. `lifecycleStage != .archived`, `!purged`,
volume-currently-reachable) and feeds the per-target machinery.

No background / foreground distinction exists. Today every scan is
"foreground" in the sense that the user kicked it off and it shows up
in a job row.

### 5. Family-specific model

Long-arc plan already documented in three docs:

- `docs/family_media_training_model.md` — full architecture (ArcFace
  frozen + small classifier head → vector index → query engine)
- `docs/Media_Analyzer.md` — research on *why* generic recognizers fail
  on a family (genetic similarity, age drift, source drift)
- `docs/media_longterm_plan.md` — the four-disposition vision (Master /
  Backed up / Ready for LTA / Archived)

**Phase 1 of the plan is "frozen backbone + classifier head."** Days to
set up, hours to retrain. No code yet — this is research.

Today's reality:
- ArcFace runs as the embedder (per `project_arcface_engine` memory)
- Embeddings are computed at scan time and consumed for nearest-neighbor
  on the reference set
- Embeddings are **not** persisted as a vector index. The match is
  done one video at a time against the in-memory reference set.

For Rick's stated wish — *"so when I say 'this is donna' [you can] 'find
matt'"* — what's needed is closer-to-home than full classifier training:
**a persistent vector index keyed by `confirmedByUserPeople` would let
"this is Donna" entries become reference embeddings that the next Find
Person run consults directly**, without needing a custom classifier.
That's an intermediate value-stop between today and the long-arc
classifier.

## Suggested priority + rough effort

Smallest, highest-leverage first. Each row stands alone.

| # | item | effort | unlocks |
|---|---|---|---|
| 1 | Pick scope option A / B / C above and wire the Catalog tab accordingly | A: ~30 min; B: ~2 hrs; C: ~1 hr + tests | Rick can search "birthday cake" / "happy anniversary" across the catalog the moment any caption work runs |
| 2 | Add `confirmedByUserPeople` field to `VideoRecord` (additive optional, Codable backward compat per the `MediaDisposition`/`statusRaw` precedent) + plumb into `matchesQuery` + `CatalogQueries.peopleCount` | ~2 hrs + tests | Schema for definite-vs-suspected distinction |
| 3 | "Confirm person on this record" UI in `InspectorPanel` — add/remove/promote name; promote = move from detectedPeople → confirmedByUserPeople | ~3 hrs | Rick can do the manual tagging he wants today |
| 4 | "Caption All Cataloged" + "Find Family Across Catalog" entry points — wrap the existing per-target engines in a catalog-records iterator with a predicate (online + non-archived + not-already-done) | ~4 hrs | The catalog-wide scan Rick asked for; uses existing engines, no new ML work |
| 5 | Pause / Resume parity for catalog-wide scans matching the Find Person model (descriptor on disk, statusRaw, cache-skip resume) | ~3 hrs | Catalog scans survive app restart — same pattern as Find Person |
| 6 | Persistent vector index keyed by `confirmedByUserPeople` references | ~1-2 days | "Confirmed Donna" entries become reference embeddings; Find Person re-runs hit them automatically. Intermediate value-stop before classifier training. |
| 7 | Background-priority scan mode (lower QoS Task, surfaces in dashboard but doesn't block UI; pause/resume from anywhere) | ~1 day | The background-scanning split Rick described |
| 8 | Family classifier head training (per `docs/family_media_training_model.md` Phase 1) | weeks of off-line work | Long-arc accuracy gain on cases the pretrained models miss |

Items 1–3 together close 80% of Rick's daily friction with very modest
code investment. Items 4–5 are the catalog-wide scan loop. Items 6–8 are
the ML accuracy arc.

narrow matcher with captions + transcripts. Smallest, lowest-risk,

## Open questions for Rick

These need a decision before any of items 2-3 land:

1. **Storage shape for confirmedByUserPeople.** Is it a flat
   `[String]` (parallel to detectedPeople), or a richer
   `[ConfirmedTag]` with `{ name, confirmedAt: Date, confirmedBy:
   String }` so we can show provenance later? I'd vote the richer
   form — costs nothing in storage, opens "you tagged this on
   2025-04-12" UI later, and matches the `purgedAt` precedent.

2. **What does "confirm" mean when an automatic tag is wrong?**
   Three options:
   - (a) Confirm-only: confirmedByUserPeople grows; detectedPeople
     stays as-was. Search returns either.
   - (b) Confirm-and-remove: confirming Donna removes any conflicting
     detectedPeople entries on this record.
   - (c) Reject: a separate `rejectedPeople: [String]` that suppresses
     future auto-tag of that name on this record (e.g. "no, that's
     Anna, not Donna").
   I'd vote (c) is the right semantic, but (a) + (b) together cover
   the immediate need.

3. **Caption-search ranking**: when a search matches both filename and
   caption, does the filename match rank higher? Or are they pooled?
   This affects results UX but not the data model.

Pick once, ship.
