# Scene Captions — Integration Plan

*A plan for adding vision-language scene captions to the catalog as a
sibling annotation to person tags. Written 2026-05-22 to coordinate
with the family-tagging work happening on `feature/family-tagging-writeback`.*

## Goal

Every cataloged video should eventually carry two independent annotation
families:

1. **People** — "Donna appears at 1m24s–1m39s." Handled by the
   PersonFinder pipeline and written back via `applyDetectedPeople`
   (the family-tagging branch).
2. **Scene captions** — "A man is sitting in a kitchen playing guitar."
   Generated by a vision-language model and written back via a parallel
   path (this document).

Together they make the catalog **searchable in natural language**: a
user types "Donna playing guitar" and the catalog filter hits both
person tags (Donna) and caption text (playing guitar).

Scene captions do *not* identify anyone — they describe setting,
activity, count, and visible text. Identity remains the job of the FD
pipeline.

## Where it fits in the long-arc plan

This is enrichment metadata in service of [Media Long-Term Plan](media_longterm_plan.md):
the better the search, the easier it is for Rick (and family) to find
videos worth promoting to Master / Backup / Ready-LTA. It is
**complementary to face-ID**, not a substitute — see
[catalog-aided-face-detection.md](catalog-aided-face-detection.md) for
the FD north star.

## Schema

Two new fields on `VideoRecord`, mirroring the shape of the
`detectedPeople` field landing on `feature/family-tagging-writeback`:

```swift
struct SceneCaption: Codable, Hashable {
    let timestamp: Double   // seconds into the clip
    let text: String
}

// On VideoRecord:
var sceneCaptions: [SceneCaption] = []
var sceneCaptionModel: String? = nil   // e.g. "qwen2.5-vl-3b-4bit"
var sceneCaptionDate: Date? = nil      // when captioned
```

Provenance (`sceneCaptionModel`, `sceneCaptionDate`) lets us re-caption
later with a better model and know which records are stale. Per-frame
timestamped captions compose naturally with the presence-segment shape
that `detectedPeople` will grow into — both answer "what happens at
which times."

### Why not unify under a generic `Tag` type

The temptation is to bury `detectedPeople`, `sceneCaptions`, `notes`,
`archiveStatus`, and `videoOnly` under a single `tags: [Tag]` union.
Resisting that for now — each one has different semantics (enum,
flat strings, timestamped structured data, free text, bool), and a
premature union costs type safety on the things that matter
(`archiveStatus` is the obvious example). Field-by-field for v1;
revisit if/when keeping them parallel starts to hurt.

## Pipeline

Three stages, run independently:

| Stage | Trigger | Driver | Output field |
|-------|---------|--------|--------------|
| 1. Catalog scan | "Scan Volume" | existing scanner | `VideoRecord` per file |
| 2. Person tagging | "Find Person" | PersonFinder + `applyDetectedPeople` | `detectedPeople` |
| 3. Scene captioning | **"Caption Videos"** (new) | `CaptionRunner` (new) + `applyCaptions` (new) | `sceneCaptions` |

Stages 2 and 3 are independent — order doesn't matter, neither blocks
the other. Both write back to the same catalog records. Per-volume
button UI to match the existing PersonFinder pattern; do not auto-run
after every catalog scan (captioning ~1000 videos is ~2 hours, the
user should opt in).

## Implementation: Swift native via `mlx-swift`

**Preferred path.** Use Apple's [`mlx-swift`](https://github.com/ml-explore/mlx-swift)
and the [`mlx-swift-examples`](https://github.com/ml-explore/mlx-swift-examples)
LLM/VLM samples to run Qwen2.5-VL directly from the Swift app. Same
model weights (`mlx-community/Qwen2.5-VL-3B-Instruct-4bit`), same
arithmetic, no Python subprocess.

Why preferred:

- **No Python venv on user machines.** The shipping app stops depending
  on `venv-mlx`. Less to install, fewer ways to drift.
- **Native progress reporting.** Captioning progress per frame flows
  directly into the existing per-job console UI used by PersonFinder.
- **Apple Silicon learning exercise.** Rick wants to understand the
  mlx-swift integration shape; this is a low-risk place to learn it.
- **Composes with other MLX features later.** If we ever do LLM-based
  catalog summarization or VLM-based junk detection, the integration
  cost is already paid.

What we have to figure out:

- Concrete `mlx-swift` API for VLM (image + text → text). The samples
  cover LLMs; VLM support is newer.
- Model loading lifetime (load once per Caption job, dispose at job end).
- Concurrency: one model instance, frames serialized through it.
  Multiple jobs in parallel should each have their own instance —
  same lesson learned from [[project-arcface-concurrency-bug]].
- Frame extraction: keep using AVFoundation (CGImage at timestamp),
  same approach as the existing FD pipeline. No ffmpeg dependency on
  the Swift side.

### Fallback: Python subprocess wrapper

If `mlx-swift` integration hits a wall (missing VLM support, performance
regression vs Python, memory issues), the fallback is the
already-working `scripts/vlm_caption.py` driven via `Process()` — the
same pattern `PersonFinderModel` uses for `face_recognize.py`. Fallback
is **plan B, not the goal**; do not start there.

## UI

Per scan target in the catalog UI, add a **"Caption Videos"** action
alongside the existing "Find Person" action. State machine:

- *Idle* — show "Caption Videos" button.
- *Captioning* — show progress (file N of M, model load %, last caption
  preview). Allow cancel.
- *Done* — show "Re-caption" (uses current model) and a count of
  records captioned with this model vs an older model.

A small icon in the catalog table marks records that have captions.
Click expands inline to show timestamped captions; double-click a
timestamp jumps the video preview to that frame.

## Search

For "man playing guitar" search, or better Rick playing guitar (!) eventually, but for now implement in stages.

- **v1:** linear substring match across `sceneCaptions[*].text` for
  every record in the filtered set. With a few thousand records the
  cost is microseconds — no infrastructure needed.
- **v2 (if catalog grows past ~10k records):** SQLite FTS5 over a
  concatenated `caption_text || ' ' || detected_people_text` column.

The existing catalog filter UI grows one new toggle, or the unified
search bar treats captions/people as additional searchable text
alongside filename and codec. UX detail TBD — defer until v1 is in
place and Rick has tried it on a real catalog.

## Sequencing

Per Rick's explicit preference:

1. **`feature/family-tagging-writeback` rebases and merges to main.**
   Stability check (Python suite, then Swift suite on M4/M1 via
   [[feedback-offload-tests]]).
2. **`feature/scene-captions` cuts off resulting main.** Adds the
   schema fields, the `mlx-swift` `CaptionRunner`, and the "Caption
   Videos" UI. Stability check. Merges to main.
3. **`feature/catalog-search-v2` cuts off resulting main.** Wires both
   `detectedPeople` and `sceneCaptions` into the catalog search UI.

Each step lands and stabilizes before the next begins. No parallel
mutation of the same files between branches.

## Coordination notes for the M4 (family-tagging) Claude

This plan is intentionally non-blocking on your work:

- **We do not touch `detectedPeople`, `applyDetectedPeople`,
  `VideoScanModel+FamilyTagging.swift`, or `FamilyTaggingTests`.**
  Your branch can land without thinking about captions.
- **We do touch `VideoRecord` to add three new fields.** They are
  additive (`Codable` defaults; older snapshots still decode). When
  your branch lands the `suspectedPeople` v3 migration, those changes
  can compose with the captions migration (call it v4 if it lands
  after, or fold into v3 if both land in the same window).
- **We do touch `CatalogStore` only if a migration step is needed.**
  Additive `Codable` fields shouldn't require one.
- **UI conflicts are possible** if both branches add buttons to the
  same per-target row in `ContentView`. Surface this when the
  captions branch starts so we can coordinate the row layout.

The Python script `scripts/vlm_caption.py` is already on main, plus
its smoke test `tests/test_vlm_caption.py`. They have **zero overlap**
with any Swift code or the family-tagging branch and are safe to
ignore from your side.

## Open questions to revisit before the captions branch starts

- **mlx-swift VLM API surface** — needs an investigation pass. If
  `mlx-swift-examples` doesn't yet support Qwen2.5-VL, we either fork
  the example or fall back to subprocess. Decision should be made
  before significant Swift code is written.
- **Caption persistence size.** 8 frames × ~50 words × ~1KB JSON ≈
  ~8KB per record. 10k-record catalog → ~80MB just for captions.
  Probably fine in JSON snapshot form; might motivate the SQLite
  migration sooner.
- **Re-caption policy.** When the model version changes, do we keep
  the old captions, replace, or keep both? Probably "replace, but
  record `sceneCaptionDate` so the user can see staleness." Decide
  at implementation time.
- **Threshold for captioning during a Find-Person job.** If we
  caption opportunistically while extracting frames for face
  detection, we can amortize the I/O. Possible v2 optimization.
