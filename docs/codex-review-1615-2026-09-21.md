## Remaining findings

1. **P1 — the uncached-keeper path rechecks retained-copy evidence before its final full read.** `DeleteDuplicatesJob.swift:203–211` falls back to verify-then-quarantine when keeper fixity is unavailable. Its ticket has `hashedInQuarantine == false`. The new tier evidence recheck at Job:249 precedes `SignatureVerification.deleteQuarantined` (Job:255), which then reads the entire quarantined file at `SignatureVerification.swift:672–688`. After that read it checks only target and keeper identities (692–695), then removes the target (719). Removing or rewriting a counted sibling during the read leaves permanent deletion authorized with only two verified copies remaining. Put the counted-copy recheck after all hashing at the final mutation guard, including this fallback.

   Deterministic regression: use the `DeleteDuplicatesCodex1611Tests` fixture, clear `keeper.contentFixity`, and change a counted sibling once in `didReadBlock("quarantine")`. Assert three-to-two downgrades to Trash; two-to-one restores the target. Existing new fixtures always supply keeper fixity (`DeleteDuplicatesCodex1611Tests.swift:152`). This scenario is source-confirmed, not executed by this review.

2. **P1 — Put Back forgets recovery when the drive is unavailable.** `DeleteDuplicatesJob.swift:1446–1449` treats `fileExists == false` as recovery and clears the quarantine reference. With SanDisk disconnected or inaccessible, Put Back/Discard can therefore forget a file that still exists on that drive. `VideoScanModel+Duplicates.swift:715–719` saves and files a completed plan; remounting the drive does not restore its recovery offer. Neither the UI nor the entry point guards drive availability. Preserve recovery obligations when absence cannot be established on an accessible drive. Test unavailable drive/quarantine, action, reconnection, and successful retry.

3. **P1 — failed restoration of an unjournaled quarantine is not retained for retry.** The deterministic directory fallback in `DeleteDuplicatesJob.swift:1337–1345` discovers a quarantine left by a crash before the ticket save. If its original path is occupied, restoration fails at 1212–1228, but the discovered directory/stamp is never installed into the entry before it becomes refused. With `quarantineDirectory == nil`, `Entry.needsRecovery` (`DeleteDuplicatesPlan.swift:444`) is false, and completion can file the plan as done. Persist the discovered recovery obligation before settling the refusal. Test crash after rename/before ticket persistence, obstructed restoration, relaunch, obstruction removal, and successful Put Back. Existing recovery fixtures explicitly record the ticket first (`DeleteDuplicatesCodex1606Tests.swift:398–399`).

Findings 2–3 concern interruption/recovery. Finding 1 affects tier authorization while a fallback file read is in progress.
